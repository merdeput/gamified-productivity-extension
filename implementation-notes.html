Focus Garden MVP Implementation Notes

Scope Decisions

  • Implemented the MVP in the project root only. The existing focus-garden-extension folder was not modified.
  • The extension action opens a Chrome side panel. The UI file remains popup/popup.html because that folder already existed.
  • Kept the implementation in plain HTML, CSS, and JavaScript with no added libraries.
  • Refactored into a small number of medium-sized modules instead of many tiny files.
  • Split the former state.js module into constants.js, utils.js, and actions.js so static values, stateless helpers, and state transitions have clear boundaries.
  • Centralized chrome.storage.local access in storage.js.
  • Reduced background.js to Chrome service-worker wiring and message dispatch.

Removed Screens

  • Removed the standalone Timer screen.
  • Removed the standalone Progress screen.
  • Removed the standalone Reward screen.
  • Removed the standalone Blocked Sites screen.

Final Compact UI Structure

  • Task List / Task Setup: create, select, rename, reset, and delete tasks.
  • Mission Setup + Timer: edit work/rest/session settings, start and control the timer, view session progress, see completion reward feedback, and edit placeholder blocked-site lists.
  • Garden Placeholder: shows saved seed total only.

Why Screens Were Merged

  • Timer controls belong next to mission settings because users configure and run the same mission object.
  • Progress is now compact text in the Mission area, such as Session 2 / 4, instead of a separate navigation step.
  • Reward feedback is a small notification inside the Mission area so mission completion does not redirect the user.
  • Blocked-site settings are only placeholder data, so they are collapsed inside Mission instead of taking a full screen.

Data Model

  • Tasks still own a mission object with totalSessions, currentSession, workDurationMinutes, restDurationMinutes, timerMode, remainingSeconds, and rewardClaimed.
  • Both task and mission objects store softBlockedSites and hardBlockedSites.
  • activeMission mirrors the currently running or paused mission so switching side-panel areas does not erase timer state.

Current Module Structure

  • background.js: Chrome listener setup, side-panel behavior, alarm handling, message routing, and alarm side effects.
  • storage.js: loads, normalizes, and saves extension state through chrome.storage.local.
  • constants.js: dependency-free static defaults and timer-mode values only.
  • utils.js: stateless helpers, formatting, timer queries, validation, normalization, reward calculation, mission initialization, and placeholder site-list cleanup.
  • actions.js: predictable task, mission, timer, scheduling, settings, reward, and garden-seed state transitions.
  • popup/popup.js: side-panel entrypoint only.
  • popup/ui.js: compact UI event handling, rendering, form payloads, message calls, and local selected-task UI state.
  • popup/popup.html and popup/popup.css: side-panel markup and styling.

Duplicate Logic Removed

  • Timer display and period calculations now come from utils.js instead of being duplicated in the UI.
  • Task and mission validation now use validateTaskInput from utils.js in both the background flow and UI validation.
  • Reward calculation is centralized in utils.js.
  • Task/mission normalization and placeholder site-list cleanup are centralized in utils.js.
  • Storage reads and writes are centralized in storage.js.

State Module Refactor

  • Removed the bloated state.js module and replaced it with three focused files.
  • Dependency direction is constants.js to utils.js to actions.js to background/UI consumers.
  • constants.js has no imports and contains static values only.
  • utils.js has no storage, DOM, Chrome API, or app-state mutation logic.
  • actions.js contains functions that accept app state and return normalized state transitions plus existing alarm hints.
  • No task, mission, timer, scheduling, settings, reward, garden placeholder, or blocked-site placeholder behavior was intentionally changed.

App Settings

  • Added a compact gear button in the top-right of the side panel. It toggles an inline settings dropdown instead of opening a separate settings screen.
  • Settings are persisted inside the existing root state object under settings through chrome.storage.local.
  • Default settings are defaultWorkMinutes: 2, defaultRestMinutes: 5, defaultTotalSessions: 4, showCompletedTasks: true, compactMode: true, and theme: "light".
  • New tasks and their new mission objects use the configured work, rest, and session defaults.
  • Changing settings does not overwrite existing tasks, existing mission configuration, active mission timers, deadline scheduling, rewards, or garden seeds.
  • Reset Settings restores only the settings object. It does not delete or reset tasks or missions.
  • showCompletedTasks filters completed task cards from the task board without deleting them.
  • compactMode adjusts layout density only.
  • theme supports light and dark. The dark theme changes presentation only and does not alter task or mission state.

Assumptions

  • Task title editing stays in the Task area; mission timing and placeholder blocking settings stay in the Mission area.
  • Mission settings are disabled while the selected mission is actively running or paused to avoid changing timer math mid-session.
  • Final work completion completes the mission directly; no final rest is required.
  • Already-earned seeds are not removed when a mission is reset.

Timer And Session Behavior

  • idle: mission can be configured and started.
  • work: work timer is running.
  • rest: rest timer is running between work sessions.
  • paused: timer is stopped and can resume into the prior work/rest mode.
  • completed: all planned work sessions are finished and reward feedback appears in the Mission area.

Timer Drift Diagnosis And Fix

  • Diagnosis: the visible countdown is rendered in popup/ui.js, which polls the background once per second with GET_STATE.
  • Diagnosis: timer transitions are centralized in actions.js through advanceTimer, while stateless queries such as getRemainingSeconds and getDisplaySeconds live in utils.js.
  • Diagnosis: the timer already stored startedAt, remainingSeconds, and timerMode, and display math used wall-clock time through Date.now().
  • Cause: while the timer was still running, advanceTimer saved the rounded whole-second remainingSeconds and reset startedAt to the current time on every poll.
  • Cause: if a poll happened before a full second elapsed, fractional elapsed time was discarded. Repeating that over many ticks made the countdown feel slower than real time.
  • Fix: running timers now keep their original remainingSeconds and startedAt baseline until pause, reset, or a work/rest transition. Each render calculates remaining time from actual elapsed wall-clock time.
  • Fix: popup/ui.js now guards against overlapping refresh calls so slow storage/message cycles cannot create stacked refreshes.
  • Result: delayed ticks should catch up on the next render instead of extending the Pomodoro.
  • No notification, sound, or new alarm feature was added for this fix.

Responsive Side Panel Layout

  • Diagnosis: the side panel CSS used a fixed body width of 410px and a fixed minimum height, so the UI did not adapt when Chrome's side panel was resized.
  • Fix: the root, body, and .app now fill the available viewport, and the active screen owns vertical scrolling. Short panels should scroll content instead of clipping it.
  • Fix: spacing, panel padding, headings, the timer, progress height, and textarea height now use clamp() where useful so the compact UI scales without becoming oversized.
  • Fix: task setup, mission duration inputs, preset buttons, and timer controls use flexible grid/flex sizing with wrapping so controls remain readable on narrow panels and spread naturally on wider panels.
  • Fix: cards, task rows, inputs, and controls use min-width: 0, overflow-wrap, and hidden horizontal overflow to avoid unwanted sideways scrolling.
  • Fix: very narrow panels stack the main tabs and row-style headers/actions using a small media query.
  • The layout remains compact and keeps the existing Tasks, Mission, and Garden screens unchanged.
  • Browser screenshot verification could not be run in this session because the in-app browser was unavailable, so validation was limited to source inspection and static checks.

Deadline Scheduling And Drag-And-Drop

  • Added deadlineDate to each task using the simple YYYY-MM-DD format.
  • New tasks default to the current local date. The date is calculated from the user's local Date object and formatted manually instead of using a hardcoded date or UTC conversion.
  • Existing saved tasks without deadlineDate are normalized to the current local date in utils.js, so older task data continues to load.
  • The Task screen now renders a compact chronological board with visible date boxes for today and the next four days, plus any other dates already used by saved tasks.
  • Empty date boxes remain visible and can accept dropped tasks.
  • Task rescheduling uses browser-native drag-and-drop events: dragstart, dragover, dragleave, and drop.
  • Dropping a card sends a focused RESCHEDULE_TASK action that updates only deadlineDate, preserving all task, mission, timer, blocked-site placeholder, and reward data.
  • The existing task actions remain on each card: select/configure, rename, reset, and delete.
  • Task action buttons are hidden by default and appear only on the currently selected task card to keep the board compact.
  • A small date input was added to the task form as a fallback for creating or editing a deadline without dragging.
  • The board uses responsive CSS grid columns so date boxes stack on narrow side panels and spread naturally when there is more width.

Current Active Mission Visibility

  • When a task other than the active mission task is selected, the Mission screen now shows a compact Current Active Mission panel above the selected task's mission setup.
  • The panel reads from the existing activeMission state only. No duplicate mission state or second active mission concept was added.
  • The panel shows the active task title, timer mode, session progress, remaining time, and the blocking message that the active mission must be completed or reset before starting another.
  • The panel includes focused actions for viewing the active mission, resetting it, or completing it when completion is already allowed by existing mission rules.
  • The normal selected-task mission setup remains visible, but the Start button is disabled while a different mission is active to make the single-active-mission rule clearer.

Mission Controls, Deadline Colors, And Optional Selection

  • Diagnosis: popup/ui.js forced a selection during refresh when selectedTaskId was empty, and getSelectedTask() also silently returned the first task. Together those fallbacks made de-selecting a card immediately jump back to the first task.
  • Fix: selectedTaskId is nullable UI-only state. Refresh, settings updates, drag-and-drop rescheduling, resets, and ordinary renders preserve a deliberate no-selection state. If the selected task is deleted or otherwise disappears, selection is cleared.
  • The Mission screen handles no selected task with the compact message Select a task to set up a mission. An existing active mission remains visible through the existing active-mission panel.
  • Mission timer controls are now hidden unless relevant: idle shows Start; running work shows Pause, Finish Work, and Reset; paused shows Resume and Reset; running rest shows Pause, Skip Rest, and Reset; completed shows Reset.
  • The existing timer transition behavior was preserved. This implementation automatically starts rest after a finished work session and automatically starts the next work session after rest finishes or is skipped, so separate rest-ready and next-work-ready controls are not currently reachable states.
  • Task cards now receive task-card--past, task-card--today, or task-card--future styling. Comparisons use normalized local YYYY-MM-DD strings from the existing date helpers to avoid time-of-day and UTC boundary errors.
  • Deadline colors use subtle red, green, and blue card treatments in both light and dark themes.

Blocked Website Placeholders

  • The UI stores soft and hard blocked-site arrays but does not block websites.
  • The compact blocked-site section is collapsed by default using a details element.
  • Future blocking logic should connect the saved arrays in background.js to webNavigation or declarativeNetRequest.

Pomodoro Audio Notifications

  • Added audio notification for automatic work-timer and rest-timer completion using assets/audios/end-of-session.mp3, the provided session-ending sound.
  • Audio events are created inside advanceTimer in actions.js, which is the existing work/rest timer transition path. Audio is not triggered from general rendering.
  • Each event stores a stable key such as missionId:sessionNumber:work_audio_played or missionId:sessionNumber:rest_audio_played.
  • The side panel attempts playback with new Audio(chrome.runtime.getURL("assets/audios/end-of-session.mp3")) and acknowledges the key through the existing background message router.
  • Acknowledged keys are persisted in audioPlayedKeys with a bounded history, preventing repeated playback during polling, re-rendering, or side-panel refreshes.
  • The existing timer flow remains unchanged: completed work automatically enters rest or completes the mission, and completed rest automatically starts the next work period.
  • A compact in-UI session alert is shown alongside the timer for work completion, rest start, next-work start, or final mission completion.
  • No web_accessible_resources entry is needed because playback happens inside the extension side-panel document using an internal extension URL.

Known Limitations

  • Blocked sites are still placeholders and do not affect navigation.
  • The garden still only shows saved seeds.
  • Only one active mission is supported at a time.
  • There are no browser notifications yet. Session completion currently uses side-panel audio and an in-UI alert.
  • There are no automated tests yet.
  • Settings defaults apply to newly created tasks and missions only; there is no bulk apply-to-existing-tasks action.
  • MV3 background service workers do not reliably play audio directly. Session audio therefore plays only while the side panel is open. Alerts older than 15 seconds are acknowledged without late playback.
  • Browser autoplay policy may still block playback. The UI keeps the visual session alert and reports the blocked audio attempt without interrupting timer behavior.
  • Rest and next-work timers still start automatically under the existing timer model, so there are no separate rest-ready or next-work-ready pauses.
